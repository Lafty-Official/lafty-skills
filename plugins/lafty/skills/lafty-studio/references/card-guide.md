# 캐릭터 카드 작성 가이드 (`character-card/v2`)

## 1. 이 앱에서 캐릭터가 사는 방식

카드는 이 전제에 맞춰 써야 잘 동작합니다.

- **DM.** 캐릭터 페이지에서 시작하는 채팅창 하나에서 며칠에서 몇 주 동안 대화가 이어집니다. 상대는 앱 사용자 본인입니다.
- **상대 정보는 대화에서 알게 된다.** 사용자의 이름, 직업, 가족, 과거는 카드에 쓰지 않습니다. 캐릭터는 대화에서 들은 것만 사실로 압니다.
- **시간을 안다.** 캐릭터는 지금 날짜·요일·시각을 알고, 하루 일과(`routine`)에 따라 "보통 이 시간에 하는 일"을 앱 메모로 받습니다. 시각은 대화의 시간대 기준입니다(기본 `Asia/Seoul`).
- **대화 사이에도 캐릭터의 삶이 진행된다.** 캐릭터는 대화와 그 사이에 있었던 일만큼만 진행과 결과를 사실로 말합니다.
- **메신저 문체.** 한국어로 보통 한두 문장씩 씁니다. 행동을 괄호로 묘사하지 않습니다.
- **카드는 대화 시작 때 통째로 고정된다.** 카드를 고쳐도 이미 시작한 대화는 옛 카드를 씁니다. 고칠 때는 `version`을 올립니다.
- **캐릭터와 만남은 따로다.** 카드는 이 사람이 누구인지를 담습니다. 사용자와 어떤 사이로 시작하는지는 만남 설정(`openings`)에 따로 씁니다. 처음 대화하는 사이, 손님, 오래된 친구처럼 한 캐릭터에 여러 만남을 두고 대화를 만들 때 고릅니다(4절 14번).

그래서 좋은 카드에는 다음이 있습니다.

- 메신저로 계속 대화할 이유
- 시간에 따라 진행되는 일
- 하루 일과
- 관계가 깊어지며 달라지는 태도

## 3. 항목별 규격

`appearance`와 `openings`를 뺀 모든 항목은 필수입니다. `identity.age`만 `null`이 될 수 있습니다. 규격에 없는 항목을 더하면 카드가 거부됩니다.

| 항목 | 형식 | 쓰는 법 |
| --- | --- | --- |
| `schema_version` | `"character-card/v2"` 고정 | |
| `character_id` | 문자열 | 영문 소문자·숫자로 시작하고 영문 소문자·숫자·`_`·`-`만, 64자 이하. 파일 이름으로도 쓰이며 캐릭터마다 달라야 한다. 예: `seoyun_clockmaker` |
| `version` | 문자열 |  |
| `identity.name` | 문자열 | 부르는 이름 |
| `identity.age` | 문자열 또는 `null` | **숫자만**(예: `"29"`). "29살."로 렌더링된다. 나이를 정하지 않으면 `null` |
| `identity.role` | 문자열 | 한 줄 역할과 하는 일. 끝에 마침표를 찍지 않는다 |
| `identity.world` | 문자열 | 사는 곳과 세계. 끝에 마침표를 찍지 않는다 |
| `premise` | 문자열 | 이 사람을 한 문장으로. 모순이나 긴장이 보이게 |
| `background` | 문자열 | 지금의 이 사람을 만든 과거와 현재 생활. 3~6문장의 산문 |
| `appearance` (선택) | 문자열, 800자 이하 | 생김새를 2~4문장으로: 키·체형, 머리 색·길이·묶는 법, 눈과 얼굴, 늘 보이는 특징, 즐겨 입는 옷. AI가 읽고, 앱이 그리는 그림이 이 글을 따른다. "관측할 때만 안경"처럼 조건이 붙은 특징은 그림에서 늘 보이지 않으니 따로 적어도 된다 |
| `values` | `{value, behavior}` 목록 | 2~4개. `behavior`는 그 가치가 행동으로 드러나는 방식 |
| `value_conflicts` | 문자열 목록 | 1~3개. 가치끼리 부딪힐 때 실제로 어떻게 하는지 |
| `drives` | `{want, fear, current_concern}` | 원하는 것, 두려운 것, 요즘 걸리는 진행 중인 일 |
| `flaws_in_behavior` | 문자열 목록 | 3~5개. 행동으로 보이는 결점 |
| `opinions` | 문자열 목록 | 3~6개. 이 사람만의 의견과 취향 |
| `voice.speech_level` | 문자열 | 높임 수준과 바뀌는 조건 |
| `voice.rhythm` | 문자열 | 메신저에서의 문장 길이와 길게 쓰는 때 |
| `voice.habits` | 문자열 목록 | 2~3개의 말버릇. 짧은 구로, 마침표 없이 |
| `voice.humor` | 문자열 | 유머의 결 |
| `voice.avoid` | 문자열 목록 | 피할 말투. 템플릿의 메신저 기본 4개는 남겨 둔다 |
| `facts` | 문자열 목록 | 2~6개. 바뀌지 않는 사실. 일하는 시간, 쉬는 날, 맡은 일에 걸리는 기간을 꼭 넣는다 |
| `routine` | `{days?, start, end, doing, place?}` 목록 | 하루 일과. 4절 7번 참고 |
| `lore` | `{topic, content}` 목록 | 2~5개. 주변 인물·장소와 지금의 상태 |
| `relationship_stages` | `{stage, behavior, entry?, mutual?}` 목록 | 3~5단계. 단계마다 달라지는 태도. `entry`(선택)는 이 단계로 넘어가려면 있어야 하는 일이며, 관계 진행 판정에 쓰고 AI에게는 보이지 않는다. `mutual`(선택, `true`)은 두 사람의 말이 모두 있어야 오르는 단계다 |
| `canon_policy` | `{fixed, improvisable, evidence_required}` | 각 2~4개의 짧은 명사구. 4절 9번 참고 |
| `greeting` | 문자열 | 대화창의 첫 메시지. **물음표로 끝나면 거부된다** |
| `examples` | `{situation, lines}` 목록 | **2~6개**, 각 대화는 2줄 이상. 줄마다 `speaker`는 `user` 또는 `character` |
| `openings` (선택) | 만남 목록, 최대 8개 | 첫 번째가 기본. 없으면 `greeting`이 모든 대화의 첫 메시지가 된다. 4절 14번 참고 |

## 4. 잘 쓰는 법

1. **규칙표가 아니라 사람을 쓴다.** "친절하다" 대신 "확인하지 못한 일을 듣기 좋게 꾸미지 않는다"처럼 행동이 보이는 문장으로 씁니다.
2. **구체적인 이름을 준다.** 가게 이름, 동네, 물건, 사람 이름이 있어야 대화가 길어져도 같은 세계에 머뭅니다.
3. **결점은 행동으로 쓴다.** "고집이 세다" 대신 "칭찬을 들으면 어색해서 화제를 돌린다"처럼 씁니다.
4. **가치는 충돌과 함께 쓴다.** 두 가치가 부딪힐 때 어느 쪽을 먼저 하는지가 성격입니다.
5. **진행되는 일을 준다.** AI는 캐릭터가 하고 있거나 하기로 한 일을 한 단계씩 진행시킵니다.
   - `drives.want`, `drives.current_concern`에 진행 중인 일을 둡니다.
   - `facts`에 그 일에 걸리는 기간을 적습니다. 예: "점검은 하루, 부품 주문은 3일에서 일주일"
   - 손님이나 상대에게서 맡는 일이 있는 직업(수리, 제작, 주문, 상담 등)이 가장 잘 동작합니다.
6. **말투를 분명히 한다.**
   - 높임 수준(해요체, 반말 등)과 바뀌는 조건을 씁니다. 예: "서로 말을 놓기로 합의한 뒤에만 반말"
   - 말버릇은 2~3개면 충분합니다. 많으면 매번 반복합니다.
7. **하루 일과(`routine`)를 빈틈없이 쓴다.**
   - `days`는 0=월, 1=화, 2=수, 3=목, 4=금, 5=토, 6=일입니다. 빼면 매일입니다.
   - 시간은 24시간 `"HH:MM"`입니다. 자정을 넘는 칸은 `start`가 `end`보다 늦게 씁니다(예: `"21:00"`~`"00:30"`).
   - **위에서부터 처음 맞는 칸이 쓰입니다.** 점심처럼 짧고 구체적인 칸을 넓은 칸보다 앞에 둡니다.
   - 쉬는 날을 따로 둡니다.
   - 하루 24시간을 덮으면 좋습니다. 빈 시간에는 앱 메모에 일과가 빠질 뿐 오류는 아닙니다.
   - `doing`은 "~한다"로 끝나는 짧은 구로, 마침표 없이 씁니다.
   - `place`(선택, 30자)에 그 시간에 보통 있는 곳을 쓰면 메신저 상태 카드에 장소로 보입니다(예: `"킷사텐 '모모'"`).
8. **아는 사람과 장소(`lore`)는 현재 상태까지 쓴다.** AI는 이 사람들의 새 말과 행동을 만들지 않습니다. 이들과 얽힌 진행은 캐릭터 쪽 행동으로만 이어집니다. 예: "○○ 댁에 다녀왔다"는 기록되지만, ○○가 한 말은 기록되지 않습니다.
9. **정본 정책(`canon_policy`)을 세 칸으로 나눈다.**
   - `fixed`: 절대 바뀌지 않는 것. 이름·나이·직업, 핵심 관계 등
   - `improvisable`: 지어내도 되지만 한 번 말하면 지키는 것. 어린 시절의 작은 일화, 취향의 세부
   - `evidence_required`: 대화나 기록에 있어야만 사실인 것. 상대와 함께한 과거, 상대의 행동·감정·동의, 맡은 일의 진행·결과. 이 세 가지는 꼭 넣습니다.
10. **관계 단계는 3단계 정도로 쓴다.** 처음 연락하는 사이, 자주 대화하는 사이, 믿는 사이처럼 나눕니다. 말투가 바뀌는 조건과 깊은 이야기를 꺼내는 조건을 여기에 씁니다.
11. **첫 인사(`greeting`)는 연락하게 된 계기를 보여 준다.**
    - 1~3문장으로 씁니다.
    - 물음표로 끝내지 않습니다. 첫 메시지가 질문으로 끝나면 이후 답장도 질문으로 끝나는 버릇이 생깁니다.
    - 첫 인사는 사용자의 역할을 정합니다. 예를 들어 "어제 맡기신 손목시계"라고 쓰면 사용자는 손님이 됩니다. 사용자의 감정이나 결정은 대신 정하지 않습니다.
12. **예시 대화(`examples`)는 서로 다른 상황으로 고른다.**
    - 4~6개를 권장합니다. 상황 예: 재촉받음, 먼저 일상을 공유함, 의견이 다름, 사과받음, 칭찬받음, 곤란한 부탁
    - 예시는 목소리 참고일 뿐 실제로 있었던 일이 아닙니다. 예시 속 사건은 대화에서 사실로 쓰지 않습니다.
    - 예시 문장은 말투만 보여 줍니다. 그대로 베낀 문장이 대화에 되풀이되지 않게, 실제로 할 법한 말을 상황마다 다르게 씁니다.
13. **관계가 깊어지는 이야기라면 단계를 5개까지 둔다.** 예: 처음 연락하는 사이 → 알아가는 사이 → 친한 사이 → 마음이 쓰이는 사이 → 연인.
    - 각 단계의 `entry`에는 그 단계로 넘어가려면 실제로 있어야 하는 일을 적습니다. 예: "서로 고민을 한 번 이상 털어놓고 받아 주었다"
    - 연애로 이어지는 단계는 성인 캐릭터에게만 둡니다. 고백처럼 두 사람의 뜻이 필요한 단계는 `mutual: true`로 둡니다.
14. **만남(`openings`)을 쓴다.** 만남 하나는 다음 항목으로 이뤄집니다.

    | 항목 | 쓰는 법 |
    | --- | --- |
    | `opening_id`, `title` | 영문 식별자와 화면에 보일 이름. 예: `wrong_number`, "잘못 온 메시지" |
    | `prologue` (선택) | 대화창에 들어가기 전에 사용자에게 보여 주는 장면. 모델에는 보내지 않는다. 첫 메시지가 왜 오는지 납득되게, 2~4문단. 문단 사이는 빈 줄 |
    | `situation` | 캐릭터 쪽에서 아는 이 대화의 시작. 대화 내내 캐릭터에게 간다. 캐릭터가 모르는 것(예: 번호를 잘못 눌렀다는 사실을 아직 모름)도 분명히 적는다 |
    | `greeting` (선택) | 캐릭터의 첫 메시지. 물음표로 끝내지 않는다. 비우면 사용자가 먼저 말을 건다 |
    | `start_stage` | `relationship_stages` 중 시작 단계의 이름 |
    | `state` (선택) | 시작 상태 0~6개. `{kind, key, text}`이고 `kind`는 `work_state`, `commitment`, `relationship` 중 하나. 대화를 만들 때 기억 수첩에 미리 들어가 첫 턴부터 앱 메모에 보이고, AI가 첫 공백부터 이어 간다 |

    - `situation`과 `state`의 `{어제}`, `{오늘}`, `{내일}`은 대화를 만든 날짜(예: "10월 21일(수)")로 바뀝니다. 대화가 길어져도 "내일"이 계속 내일로 남지 않게 하기 위해서입니다.
    - 첫 메시지에서 정해지는 상황(맡은 물건, 약속, 처음 연락한 계기)은 `state`에도 적어 둡니다. 첫 메시지 문장만으로는 몇 턴 뒤에 잊기 쉽습니다.
    - 사용자에 대한 정보는 만남에도 최소한으로 둡니다. 관계를 시작하는 데 꼭 필요한 것(예: 어제 시계를 맡긴 손님)만 씁니다.
    - 이미 아는 사이로 시작하는 만남("메신저로 몇 번 이야기했다")은 무엇을 이야기했는지와 **무엇은 없었는지**를 함께 씁니다. 예: "나눈 이야기는 그날 공연과 좋아하는 노래 정도이고, 서로의 이름 말고 사생활은 거의 모른다. 따로 만나거나 같이 밥을 먹은 적은 없다." 이렇게 적지 않으면 "우리 저번에 밥 먹었잖아요", "제 강아지 이름 기억나요?" 같은 말에 캐릭터가 없던 일을 맞장구치거나 이름을 지어낼 수 있습니다.
15. **분량.** 렌더링 결과(DM 기준) 1,200~6,500자를 권장하고, 8,000자를 넘으면 검사를 통과하지 않습니다. 서윤은 약 3,200자입니다. 너무 길면 대화가 묻히고, 너무 짧으면 성격이 흐려집니다. 작품마다 달라질 처지와 세계는 카드보다 작품 쪽에 씁니다(가이드북 1-5).

### 사용자의 호칭: `{{{PLAYER_NAME}}}`

카드의 어느 글에든 `{{{PLAYER_NAME}}}`를 쓰면, 대화를 시작할 때 사용자 페르소나의 호칭으로 한 번 바뀐다. 인사말, 만남 설정, 예시 대화 등 어디든 된다.
- 바로 뒤의 조사는 호칭에 맞춰진다. 대상은 은/는, 이/가, 을/를, 와/과, 이랑/랑, 부르는 아/야다. 예: `{{{PLAYER_NAME}}}야` → 지훈아, 도하야
- 캐릭터가 처음부터 아는 사용자 정보는 호칭뿐이다. 사용자가 페르소나 소개에 적은 것은 대화에서 드러날 때 알게 된다. 그러니 카드에 사용자의 과거나 직업을 정해 두지 않는다.

## 5. 하지 말 것

- 사용자에 대한 정보(이름, 나이, 과거, 둘이 함께한 일)를 카드에 쓰기
- 캐릭터가 AI·프롬프트·시스템을 언급하게 하기. 진지하게 물을 때의 답은 엔진이 처리합니다.
- 실존 인물이나 다른 작품의 캐릭터를 그대로 옮기기
- 미성년 캐릭터에게 연애 관계 단계를 주기. 연애가 가능한 관계라면 성인으로 둡니다.
- 모든 것을 아는 캐릭터. 아는 것과 모르는 것의 경계가 있어야 기억과 진행이 의미 있습니다.
- 괄호 행동 묘사, 하십시오체 위주의 말투, 첫 인사를 질문으로 끝내기
- 규격에 없는 항목 추가. 필요한 내용은 가장 가까운 항목에 산문으로 넣습니다.

## 6. 지금 버전의 한계

- **스토리 모드에서는 카드의 일부만 쓴다.** 이야기가 자기 관계 단계와 시계를 가지므로, 카드의 `relationship_stages`와 `routine`은 AI에게 보이지 않습니다. 나이·시기·연애 여부처럼 이야기마다 다른 사실은 카드보다 시나리오의 `world`와 역할에 적습니다.
- **스토리의 결말은 DM으로 넘어가지 않는다.** 엔딩 카드의 「DM 하러 가기」는 캐릭터 페이지로 갑니다. DM은 이 카드의 만남으로 시작하고, 스토리에서 있었던 일을 모릅니다(독자가 꺼내면 그 사람이 간 데까지만 가볍게 떠올립니다).
- **한국어 전용이다.** 음성은 없습니다. 메신저에는 다른 앱 카드에서 들여온 아이콘만 아바타로 보입니다. 스토리 그림은 앱이 그립니다(스토리 그림 생성). 들여온 표정·배경 그림은 보관만 합니다.

## 10. 넘기기 전 체크리스트

- [ ] 사용자 정보가 카드에 없다.
- [ ] 첫 인사가 계기를 보여 주고 물음표로 끝나지 않는다.
- [ ] `facts`에 일하는 시간, 쉬는 날, 맡은 일의 기간이 있다.
- [ ] 일과가 하루를 덮고, 짧은 칸이 넓은 칸보다 앞에 있다.
- [ ] `evidence_required`에 함께한 과거, 상대의 행동·감정·동의, 맡은 일의 결과가 있다.
- [ ] 예시 대화가 서로 다른 상황이고, 그 안의 일이 실제 사건처럼 쓰이지 않는다.
- [ ] 고친 카드라면 `version`을 올렸다.
